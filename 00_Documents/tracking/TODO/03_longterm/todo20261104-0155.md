# Justification, alignment and sizes imposed by the parent

created
: 20261104

Synthesis of a number of todos about the same topic, which have been removed to be replaced by this one.

## Goal

- We want to be able to justify and align lines **and possibly columns**;
- we now have the notion of **zone** which is useful in this respect

## Previous situation

- Justification is a single boolean, `LayoutOptions.justified` (already commented "will be removed"), for the whole document.
- `LineLayout` justifies:
  - *without* wrapping, all lines on the width of the longest one (`justifyOnLongestZone`);
  - *with* soft wrapping (`wrapWidth`), only the lines which were wrapped, to the wrapping width. Lines ending on a real line break are left alone.

## TODO

### Forget about the global `justified` boolean

- Accept reading files with it, but completely ignore it;
- don't try to keep backward compatibility with it.

### Line (or column) alignment

Replace the global `justified` boolean by information attached to each line (or paragraph): *start*, *end*, *centred*, *justified*.

The typical use case is typing a stela, where several kinds of lines follow one another:

~~~text
      xxxx      <- centred
    xxxxxxxx    <- centred
   xxxxxxxxxx   <- justified
   xxxxxxxxxx   <- justified
   xxxxxxxxxx   <- justified
        xxxxx   <- right aligned
~~~

- Needs a way to store it in the model/MdC (a line-level option, or a marker at the start of the line).
- Needs editor support: a menu/shortcut to change the alignment of the current line or selection, and a visible indication ;
- possibly a toolbar on top of the editor, with a selection of the options for the current line, with a combobox, and the icon for the current alignment displayed.
- alignment should not be *left* or *right* aligned, but *start* or *end*, to support right-to-left writing and keep the same aspect when reversing.
- Source: issue #12.

### Notation

`-![halign=centred]`

or

`-!![halign=centred]` as page breaks double also as line break.

In the *MdC*, line endings are optional. There are a number of important points to consider:

1. a lone text without line break can be considered as a line

2. the alignment of a line without line ending is the alignment of the previous line.
  thus:

  ~~~text
  anx-![halign=centred]
  pA-nTr
  ~~~

  would also center `pA-nTr` and be equivalent to:

  ~~~text
  anx-![halign=centred]
  pA-nTr-![halign=centerd]
  ~~~

3. for copy/pasting to RTF, most copy modes (copy as quadrant, as text runs...) will not deal with alignment.

4. Columns will have a similar `valign` option.

### Specifications

Alignment is relative to the parent container:

- the main document
- or the current zone

If the parent has a fixed width, alignment is relative to that width. If the parent has no width, it will be the width of the longest line.

### Question

Is having `halign` and `valign` worth it, or a single `align` option might do?

#### Scope

- Alignment is applied individually to each line.
- when multi-line text is selected, if it contains several aligments, the alignment selector (which normally shows the current alignment) should display a "mixed" state (as a font or style selector in word processors);
- when multi-line text is selected, choosing an alignment should apply it to all lines in the selection;
- when a zone is created, it should default to the alignment of the previous line (or the parent zone).
- when a document has explicit wrapping (because the parent has a fixed width), *justified* wrapping work a bit differently. The last line or column is automatically *start* aligned if it is not **long enough** (the meaning of “long enough” should be refined)

### Alignment and line wrapping

When the option *wrap to component width* of the *view* menu is activated, the display of the editor is not WYSIWYG, but optimised for readability.

As in most word processors, in this case, the alignment of lines should be **ignored**.
