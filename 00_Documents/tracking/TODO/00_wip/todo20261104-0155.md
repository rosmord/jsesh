# Justification, alignment and sizes imposed by the parent

created
: 20261104

Synthesis of a number of todos about the same topic, which have been removed to be replaced by this one.

## Goal

- We want to be able to justify and align lines **and possibly columns**;
- we now have the notion of **zone** which is useful in this respect

## Previous situation

- Justification is a single boolean, `LayoutOptions.justified` (already commented "will be removed"), for the whole document.
- `LineLayout` justifies:
  - *without* wrapping, all lines on the width of the longest one (`justifyOnLongestZone`);
  - *with* soft wrapping (`wrapWidth`), only the lines which were wrapped, to the wrapping width. Lines ending on a real line break are left alone.


## TODO

### Line (or column) alignment

Replace the global `justified` boolean by information attached to each line (or paragraph): *start*, *end*, *centred*, *justified*.

The typical use case is typing a stela, where several kinds of lines follow one another:

~~~text
      xxxx      <- centred
    xxxxxxxx    <- centred
   xxxxxxxxxx   <- justified
   xxxxxxxxxx   <- justified
   xxxxxxxxxx   <- justified
        xxxxx   <- right aligned
~~~

- Needs a way to store it in the model/MdC (a line-level option, or a marker at the start of the line).
- Needs editor support: a menu/shortcut to change the alignment of the current line or selection, and a visible indication ;
- possibly a toolbar on top of the editor, with a selection of the options for the current line, with a combobox, and the icon for the current alignment displayed.
- alignment should not be *left* or *right* aligned, but *start* or *end*, to support right-to-left writing and keep the same aspect when reversing.
- Source: issue #12.

## Conflicts and open questions

> To be settled by hand. The points below are where the four original todos overlap or disagree.

1. **Two different things are called "justification".** In 0093/0134 it is a property of a *line* (stretch the inter-element space to fill the line). In 0060 it is a property of the space *between two tab stops* (`justification=fill`). In 0139 it is `fill` as a *size* of a zone. Do we want one common vocabulary and one common mechanism (distribute the free space among "stretchable" slots), or three separate ones? Today the only mechanism is `LineAccumulator.justifyWidthTo`.
2. **Where does the information live?** 0093 says "information on lines", 0134 says "in the editor", 0060 wants a `%[...]` marker with `label=`, `justification=`, `orientation=`, 0139 wants option values on a zone. Do alignments become a `%[...]`-style option on a line break / paragraph, a new `TopItem`, or a field of the line's `HBox`? This decides the MdC syntax and the JS port.
3. **Scope of an alignment.** Does an alignment apply to one line, until the next change (like a tab-stop set), or to a paragraph (soft-wrapped lines)? 0060 says "we will decide later on the scope of the justifications", and 0134 implicitly wants it per line. Also: with soft wrapping, the *last* line of a paragraph is not justified. Is that still right when the user explicitly says "justified" for a line that ends on a hard break (as in the stela example)?
4. **Explicit justification versus the current "only wrapped lines" rule.** In 0134's example the three "justified" lines end on real line breaks, which `LineLayout` currently leaves alone when wrapping is on. And without wrapping, they are justified on the *longest* line, not on a chosen width. A target width has to come from somewhere: longest line, `wrapWidth`, page width (see the page-size roadmap item), or a zone width.
5. **Tab stops versus alignment.** A tab-stop segment *is* a small aligned area (left/right/justified between two stops). Should centred/right-aligned lines be expressed with tab stops (a line is a segment between the margins), or are they separate? 0060's "space on the left / on the right / justification" and 0134's "centred / right aligned / justified" are the same list.
6. **Orientation.** 0060 wants horizontal and vertical tab stops, "contextual" by default. 0093/0134 only speak of lines. What is the vertical counterpart of a centred or right-aligned line in column mode (centred or bottom-aligned column)? Linked to 0116 (columns do not justify yet).
7. **Zones.** 0060 says tab stops could be scoped to a zone "once that works"; 0139 makes zone sizes depend on the line. Both need a second layout pass. Can they share it, and in which order (tab stops first, then `fill`, or the reverse)? Zones can nest, so the order matters.
8. **Interaction with soft wrapping.** Alignment of wrapped lines, tab stops reached after a wrap, and a `fill` zone whose "room left in the line" depends on where the wrap happens.
9. **Numbering confusion: two files carry the number 0139.** `00_wip/todo20261028-0139.md` is "Finish the Javascript port"; `03_longterm/todo20261028-0139.md` is "Zone sizes imposed by the parent". Only the second one is merged here. One of them should get a new number (the README says numbers are never reused).
10. **Two files exist for 0060.** `00_wip/todo20260726-0060.md` has the content; `03_longterm/todo20260726-0060.md` is empty. Probably a leftover of a move.
11. **Status.** 0060 is in `00_wip`, 0134 in `01_easy`, 0093 and 0139 in `03_longterm`. The merged todo cannot be "easy": I filed it under `03_longterm`, but a first slice (per-line alignment, with the MdC marker) could be split off as an easy or important todo.
12. **`justified` boolean.** It is already commented "will be removed" in `LayoutOptions`. It is also stored in `DocumentPreferences` and exported/imported by the JS port. Removing or keeping it as a *default* has to be decided before the line-level information is added.

## JS port

All of this changes the layout (`LineLayout`, `ColumnLayout`, `LineAccumulator`) and so must be mirrored in `jsesh-js/packages/core` (`render/layout.ts`), with new fixture variants exported by `jseshJsExport`, as was done for soft wrapping.
