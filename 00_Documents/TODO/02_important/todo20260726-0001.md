# Remove singletons

The Great Singleton Hunt: reduce the codebase's reliance on singletons and
static factories, in favour of explicit dependencies.

- [ ] give a better name to `getSuitableSignsForCode`
- [ ] remove `HieroglyphicDrawerDispatcher` from `DrawingSpecificationsImplementation`
- [ ] change `AbsoluteGroupBuilder.createAbsoluteGroupFrom`
- [ ] remove references to `MDCEditorKit` (or de-singletonise it)
- [ ] fix the creation of `ViewBuilder`; think about the `Layout` class
- [ ] introduce a facade to the whole glyph system

Basically:

- we need to differentiate the various dimension choices from the choice of
  various data sources (mainly glyph info);
- introduce a facade there (Specification, Preferences, Config... ?):
  - Preferences would be nice for plain user-selected info;
  - Config or Specification for more structured stuff;
- fix:
  ~~~java
  // Awful patch for now. This should move to another class. The font
  // manager should associate glyph codes to drawings; a code manager
  // should associate MdC codes to glyph codes.
  if (!GardinerCode.isCanonicalCode(code))
      newCode = HieroglyphDatabaseFactory.getHieroglyphDatabase()
              .getCanonicalCode(code);
  ~~~
- glyph canonicalisation should still be easy to use. For instance in:
  ~~~java
  @Override
  protected boolean equalsIgnoreIdAux(ModelElement other) {
      Hieroglyph o = (Hieroglyph) other;
      HieroglyphDatabaseInterface manager = HieroglyphDatabaseFactory.getHieroglyphDatabase();
      return manager.getCanonicalCode(this.code).equals(manager.getCanonicalCode(o.code))
        ...
  ~~~
  `getCanonicalCode` should be accessible without any problem. Some kind of
  `CoreMdCCatalog` class?

Note: `ManuelDeCodage` itself is also a singleton, but that one can probably
stay as-is. It only deals with the basic Gardiner list, and it would only be
annoying if we had different versions of the Manuel to support, which is not
currently the case.
