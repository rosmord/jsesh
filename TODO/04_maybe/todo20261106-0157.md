## How it works today

Not MVC. It is an *imperative refresh driven by events*: the widget is passive, and a controller class pushes the state into it whenever something may have changed.

Classes (module `jseshAppli`, package `jsesh.jhotdraw.documentview`):

- `JSeshViewComponent`: builds and owns the `JComboBox<LineAlignment> lineAlignmentComboBox`, the `lineAlignmentLabel`, and two display flags (`lineAlignmentRightToLeft`, `lineAlignmentVertical`). The flags are used by the combo renderer to choose the icon (`LineAlignmentIcon`) and by `updateLineAlignmentLabels()` to switch the label and tooltip between "Line" and "Column" (resource keys `lineAlignment.*` / `columnAlignment.*` in `jseshLabels`). `setLineAlignmentLayout(rtl, vertical)` stores the flags and repaints.
- `JSeshViewCore`: the controller. It wires everything.
  - **model → view**: the inner class `MDCLineManager` (a `MDCModelEditionAdapter`) is registered with `getEditor().getWorkflow().addMDCModelListener(...)`. It calls `updateLineAlignmentComboBox()` from `caretChanged`, `textChanged` and `textEdited`. The same method is also called explicitly from the constructor, `setCurrentDocument(...)` and `setJSeshStyle(...)` (hence also from `setTextOrientation`, `setTextDirection`, `setFontInfo`).
  - `updateLineAlignmentComboBox()` reads `workflow.getTextOrientationAtCaret(...)`, `workflow.getTextDirectionAtCaret(...)` and `workflow.getLineAlignmentAtCaret()`. An empty `Optional` means "mixed alignments" and becomes a `null` selection in the combo (the renderer then shows the "mixed" label).
  - **view → model**: an `ActionListener` on the combo calls `changeLineAlignment()`, which calls `workflow.setLineAlignment(alignment)` (one undo step) and gives the focus back to the editor.
  - **feedback guard**: the boolean `updatingLineAlignment` is set while the program calls `setSelectedItem`, so that the action listener ignores the programmatic change.
- `JMDCEditorWorkflow` (module `jsesh`, `jsesh.ui.editor`): `getLineAlignmentAtCaret()`, `setLineAlignment(...)`, `alignmentForNewBreak()`, `alignmentOfLineEndingAt(...)`. The alignment is *not stored in the UI*: it is read from the `LineEnd` items (`LineBreak` / `PageBreak`) of the model, so there is a single source of truth. This part is fine and should stay as it is.

Cost: each caret move rescans the lines touched by the selection. It is cheap; there is no need to optimise.

## What is fragile

1. **Easy to forget a call site.** Every path which changes the "context" (document, style, orientation, direction) must remember to call `updateLineAlignmentComboBox()`. A direct `getEditor().setJSeshStyle(...)` (which bypasses `JSeshViewCore.setJSeshStyle`) would leave the combo stale. `setCurrentDocument` already needs its own explicit call for this reason.
2. **The widget is used as a model.** The combo's own selection is the only copy of the "displayed" state, hence the `updatingLineAlignment` guard against the feedback loop.
3. **Not testable without Swing.** The logic (mixed state, label/icon choice, apply-on-select) is spread over `JSeshViewCore` and `JSeshViewComponent`. The workflow side is tested (`JMDCEditorLineAlignmentTest`); the UI side is not.
4. **Not reusable.** A Format menu (radio items), keyboard shortcuts or the web editor would each need to re-derive "what is the current alignment, is it mixed, is it a line or a column, left-to-right or right-to-left", and each would need its own refresh calls. The web editor (`jsesh-js`) has no alignment UI yet and would repeat the same logic in TypeScript.
5. Other toolbar/menu widgets (zoom combo, text direction and orientation menus) may follow the same pattern. **To check** before deciding on a general solution: we have not looked.

## Proposed direction (if and when we do it)

Do **not** build a full MVC framework for a single combo box. Take the intermediate step: a small presenter with an observable state.

1. A value object, e.g. `LineAlignmentState(Optional<LineAlignment> alignment, boolean rightToLeft, boolean vertical)`. As a record, `equals` gives change detection for free.
2. A presenter, e.g. `LineAlignmentPresenter`, with no Swing import:
   - `refresh()`: recompute the state from the workflow and the style; notify listeners **only if the state changed**;
   - `select(LineAlignment)`: calls `workflow.setLineAlignment(...)`;
   - `addListener(...)`.

   It follows the pattern of `PageSpecificationPresenter` (`jsesh.jhotdraw.preferences.document.ui`), which already exists in the project.
3. The view (combo, label, icon) only subscribes to the state and calls `select(...)`. The `updatingLineAlignment`-type guard does not disappear completely, because `JComboBox.setSelectedItem` fires its action listener. It moves into the small Swing adapter which binds the presenter to the combo; the presenter itself has no guard. An alternative is a custom `ComboBoxModel` backed by the presenter state.
4. One event instead of scattered calls: let the editor/workflow fire a single "caret context changed" notification (caret, text and style combined), so that `JSeshViewCore` no longer has to call `update...` from `setJSeshStyle`, `setCurrentDocument`, etc. Decide whether it belongs in `JMDCEditor` (module `jsesh`, usable by embedders) or only in `jseshAppli`.
5. Placement and layering: if embedders of the library may want it, put the presenter and the state in `jsesh.ui.editor` (module `jsesh`; no Swing widgets, and respect `00_Documents/documentation/jsesh-package-dependencies.md`). Otherwise keep it in `jseshAppli`, `jsesh.jhotdraw.documentview`. Recommendation: `jsesh.ui.editor`, because the state logic is toolkit-independent and the JS port can mirror it.
6. JS port: when the web editor gets an alignment UI, mirror the state and presenter in `jsesh-js/packages/` (keeping the Java names, as the port does elsewhere) rather than rewriting the logic.

## When to do it (triggers)

Do it when **the second consumer** appears, whichever comes first:

- the Format menu entry and shortcuts from the main alignment todo (radio items must show the current/mixed state);
- the web editor alignment UI;
- `%zone[align=...]`, if it changes what "the current alignment" means at the caret (zone default vs line override).

Until then, leave the code as it is.

## Things to remember when implementing

- Menus and shortcuts: before choosing a binding, grep all the action and menu definitions (Shift and Alt variants included), check the macOS system shortcuts (see `CLAUDE.md`), and list the conflicts checked.
- i18n: all labels stay in `jseshLabels`.
- Keep the behaviour:
  - the mixed state shows no selected item;
  - selecting applies to all the lines of the selection, in one undo step;
  - the editor gets the focus back after a choice;
  - labels switch to "Column" for vertical text;
  - icons depend on right-to-left and vertical.
- Tests: add Swing-free tests for the presenter (state computation: single line, mixed selection, text without line break, right-to-left, vertical, document switch, style change; no notification when the state is unchanged). Keep `JMDCEditorLineAlignmentTest`.
- Run the full Gradle build and the JS tests (see `CLAUDE.md`), even though no layout is touched.
- It is a UI change, which can't be tried from the command line. End the work with "not tried in the running app" and a manual checklist, including:
  1. first window at startup vs a window opened with Cmd-N;
  2. empty document;
  3. caret in a centred line, then in a justified one: the combo follows;
  4. multi-line selection with mixed alignments: the combo shows no selected item; choosing a value applies it to all lines;
  5. left-to-right vs right-to-left text;
  6. horizontal vs vertical text (label "Column:", vertical icons);
  7. switching between two documents;
  8. changing the text direction/orientation from the menu while the caret stays put;
  9. undo after choosing an alignment (one step).
